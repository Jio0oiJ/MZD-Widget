## 一、已修复的真实 bug

### BUG-1　BLE 诊断计数指数虚增（数据错误，影响排查）
- **位置**：`Prefs.noteBleDiag()` ← `BleScanService.persistDiag()`
- **现象**：主界面「BLE 诊断」和通知栏的回调/命中/解锁/上锁/失败计数逐次翻倍，越跑越大，完全失真。
- **根因**：`persistDiag()` 传入的是**自服务启动以来的内存累计值**（`diagCb` 等），但 `noteBleDiag()` 内部实现是 `putLong("cb", prefs原值 + cbAdd)` —— 把累计数当增量一次次累加。第一次落盘 10，第二次把新的累计 20 再加到 10 上得 30，第三次 30+30=60……指数放大。
- **修复**：`noteBleDiag()` 改为**覆盖写入**累计快照（参数 `cbAdd`→`cbTotal` 等），与调用方语义一致。
- **影响**：仅诊断显示，不影响控车逻辑。修复后计数为真实值。

### BUG-2　旧兜底闹钟残留会在一键启动步骤2误解锁（安全隐患）
- **位置**：`WidgetActions.onReceive()` 的 `ACTION_SMART_UNLOCK` 分支
- **现象**：从旧版本覆盖安装后，系统里可能残留已排定的 18 秒兜底闹钟。它触发时会无条件补发 `unlock`，而新流程此刻可能正在步骤2「等待启动确认」——恰好破坏 v1.8「未确认发动机启动绝不解锁」的核心保证，出现启动中开门。
- **根因**：v1.8 停用了兜底闹钟的**调度**，但遗留了**接收分支**，且新流程只在失败路径 `cancel` 闹钟，覆盖安装前排的闹钟不在取消之列。
- **修复**：该分支改为只记一条 log、绝不发指令。注释说明原因。

### BUG-3　行驶中离开后闩锁卡死，回家再也不自动解锁（功能性逻辑错误）
- **位置**：`CarActions.onBlePresent()`
- **复现链**：
  1. 靠近 → 解锁，闩锁置位 `true`
  2. 用户启动车辆开走 → 看门狗判离开 → `present=false`，`onBleAbsent` 查到 `started=true` → 按设计「保持现状、闩锁不复位」
  3. 到目的地熄火，此时人早已离开、`present` 仍是 `false`，看门狗因 `present==false` 不再触发 `onBleAbsent`，**闩锁永远不会被复位**
  4. 人回来靠近 → `onBlePresent` 见闩锁 `true` → 直接跳过解锁 → **车再也不会自动开**
- **根因**：闩锁的复位只挂在「离开上锁」路径上，而「发动机启动后离开」这一分支刻意不复位，又没有其他复位出口。旧实现在 `onBlePresent` 开头无条件信任闩锁。
- **修复**：`onBlePresent` 改为**以实时车况为准**：
  - 车明确已解锁 → 置闩锁、跳过（防重复）
  - 车明确已锁 → **先清残留闩锁 + 发解锁**（无论旧闩锁值），解决卡死
  - 车况查询失败 → 闩锁置位则跳过（防网络抖动误发），未置位则按「靠近务必开」发一次
- **说明**：这调整了靠近解锁的判定优先级，但保留了闩锁防重复的核心目的，且只多了「车已锁」这一确定状态判断。

### BUG-4　通知栏「判定」文案在从未发现设备时显示错误（显示 bug）
- **位置**：`BleScanService.guardText()`
- **现象**：`lastSeen==0`（还没扫到过目标）时，`now - lastSeen` 是当前时间戳的巨大数值，熄屏分支会显示「即将判离开」，但实际上根本没进入离开判定。
- **修复**：开头加 `if (lastSeen <= 0) return "尚未发现目标 · 暂不判定离开";`

### 附：2 处注释错误（上轮已修，本轮一并核对）
- `Prefs.btRssiThreshold` 注释：RSSI 范围写反为「-100（极近）~-30（极远）」→ 改为「-100（极远）~-30（极近）」，并修正「0/正数导致永远解锁」的错误因果。
- 判定清单第 9 节同一笔误同步修正。

## 二、复核后确认「非 bug / 设计取舍」的点（未改动，供你确认是否符合预期）

1. **靠近失败仍解锁 vs 离开失败不上锁**：`onBlePresent` 车况查询异常仍按「靠近务必开」发解锁；`onBleAbsent` 车况查询异常跳过上锁。是刻意的不对称（求「务必开」+「绝不误锁」）。
2. **车况状态未知时离开**：`onBleAbsent` 中 `started/unlocked` 均为 null（接口异常但未抛错）时会落到发上锁分支。是否应视同「查询失败」跳过？**建议确认**。
3. **10 秒窗口进程内不落盘**：进程重启后归零，理论上可能比预期更快发出下一条 BLE 指令。可接受。
4. **熄屏 90 秒固定阈值**：不随用户设置的「离开判定时间」变化；本版已从 60 秒放宽到 90 秒。
5. **`SMART_RUNNING` 并发守卫**：一键启动流程占用时再次点击返回「进行中」，不排队。符合预期。
6. **一键启动重发次数上限**：lock 2 次 / start 3 次 / unlock 3 次，是防 `goAsync` 死循环的工程护栏，未做无限重发。

## 三、设计权衡：一键启动车况请求翻倍（v1.8.5 已修复）

原 `CarActions.query()` 每 2 秒查一次车况，同时 `requestFastRefresh()` 触发桌面快刷、快刷又查一次，加上开头 `startFastRefresh()` 排的 10 秒 tick 和流程结束的 `refreshAndUpdate()`——一键启动期间实际有 **4 个请求来源**。

用户反馈账号有请求频率限制，要求相邻请求至少 2-3 秒。v1.8.5 已修复：
1. `query()` 查询结果通过 `CarWidget.publishStatus()` 直接写桌面缓存并重绘，**不再发快刷广播**、不再查网；
2. 删除一键启动开头 `startFastRefresh()` 和收尾的 `refreshAndUpdate()`（改为纯重绘 `redraw()`）；
3. `query()` 加入**硬节流**：任意两次 `/car/status` 间隔不足 3 秒则补足等待；
4. 轮询间隔由 2 秒改为 **3 秒**。

结果：一键启动每轮只剩 1 次 `/car/status`，且全程相邻请求间隔 ≥3 秒。桌面车况仍实时（复用本轮结果）。其它链路（桌面按钮、5 分钟周期、BLE）未改动。
