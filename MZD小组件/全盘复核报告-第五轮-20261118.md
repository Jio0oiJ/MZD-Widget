日期：2026-11-18
版本：v1.9.5（code34）→ **v1.9.6（code35）**
权威源码：`mzdwidget_build/app/src/main/java/com/example/mzdwidget/`

## 一、本轮方式

三路只读审查 Agent 并行：① 状态机/并发冲突；② 纯逻辑与边界；③ 跨模块接口契约。主审逐条独立核实代码事实后才决定修或留，重点找模块间逻辑冲突、共享状态竞态、生产方/消费方语义不一致。所有修复均经主审亲自读码确认，不照单全收。

## 二、确认并已修复的问题（8 项）

### 1【严重·安全底线】engine 字段缺失时 BLE 靠近可在行驶中解锁
- 两路 Agent 独立发现同一问题。`Api.getStatus` 在响应缺 `engine` 字段时 `started` 保持 null；`CarActions.onBlePresent` 的安全拦截只判 `started==true`（`Boolean.TRUE.equals(null)` 为 false，不拦），而 `statusUnavailable` 只在 `started==null && unlocked==null` 时拒绝——于是 `started==null, unlocked==false` 会通过全部检查，落到「已锁→解锁」分支下发解锁。
- 危险场景：车辆实际正在行驶（很多车启动后自动落锁 → unlocked=false），BLE 瞬时漏扫→重靠近，若此刻响应恰缺 engine，就会在行驶中开门。正是 `onBlePresent` 注释声称已防住的场景。
- **修复**：解锁前要求 `started` 明确非 null 且明确为 false。`started==null` 按不可用跳过、回调 false 复位 present 待重试；`started==true` 拦截行驶态。原「走到这里必然未启动」的断言现在才真正成立。

### 2【中·安全底线】engine 状态未知时 BLE 离开可盲锁、把人锁在车里
- 对称问题：`onBleAbsent` 上锁前只拦 `started==true`，`started==null, unlocked==true`（门开着、发动机状态未知）会走到 `lock()`。
- **修复**：上锁同样要求 `started` 明确为 false；`started==null` 一律跳过保持现状，不动闩锁。

### 3【中】engine 为 JSON null 被误判「明确未启动」
- `Api.getStatus` 用 `d.has("engine")` 判定，而 `JSONObject.has()` 对值为 `NULL` 的键也返回 true，`optInt` 解析 "null" 取默认 0 → `started=false`。
- **修复**：先排除 `null/JSONObject.NULL`，缺失或显式 null 保持 started=null（未知）；真值仍用 optInt 解析，保留对字符串数字（如 "3"）的兼容。

### 4【中】lock 门字段值为 null 时误判「已锁」
- v1.9.5 的 `hasDoorField` 用 `lock.has(k)`，对值为 NULL 的键也返回 true，四个门字段全 null 时算出 unlocked=false，绕过不可用保护。
- **修复**：`hasDoorField` 改为检查 `lock.opt(k)` 非 null 且非 `JSONObject.NULL`。

### 5【中·并发】切号时 epoch 与凭证快照非原子
- `CarStateCache.queryOnce` 原来在锁外读 `myEpoch`，又在别处读 token/carid。切号（写新 token → invalidate 递增 epoch）若夹在两者之间，会用新 token 查询却记着旧代次，回来后误判 stale 丢弃、白等一轮。
- **修复**：代次与 token/carid 在同一 `synchronized(lock)` 临界区一次性快照。

### 6【中·并发】桌面刷新的 cached+lastError 双读竞态
- `CarWidget.refreshAndUpdate` 原来分两次加锁调 `snapshot()` 和 `lastError()`。中间若切号 invalidate（清空两者），会出现「已取到旧账号 s + 读到清空后的 lastError==null」→ 把旧车况写盘冒充实时，正是 v1.9.4 想消除的问题的残留窗口。
- **修复**：CarStateCache 新增原子方法 `snapshotWithError()`（一次加锁同取），refreshAndUpdate 改用之。

### 7【低】未登录时 BLE 回调缺失致 present 卡死
- `onBlePresent/onBleAbsent` 开头 `if (!isLoggedIn) return` 不回调，但服务侧已 `setPresent(true)` + 占 10 秒窗口，导致 present 卡 true 直到看门狗判离开、期间无日志。
- **修复**：两处早退均 `cb.onResult(false, ...)`，让服务复位 present。

### 8【低】BLE 常驻通知在查询失败后仍显示旧车况
- `BleScanService.carStatusText()` 只读 `widget_status_json`，不读 `widget_status_err`。查询失败后桌面已正确显示「获取失败」，通知却拿旧 JSON 冒充实时。
- **修复**：先读 err，非空返回「车况获取失败」，与桌面口径一致。

## 三、本轮未改的取舍（需实机/产品拍板，改动触及核心状态机）

- **M3｜确定性跳过后 present 锁死**：`onBlePresent` 因「已解锁/发动机启动」确定性跳过返回 ok=true，present 保持 true；若之后车原地熄火落锁但 BLE 一直扫到（lastSeen 持续刷新，看门狗不判离开），present 不翻转，本停靠周期不再触发靠近解锁。这与「一次靠近只解锁一次」闩锁设计的边界重叠，改动会触及反复论证的在场/闩锁状态机，风险高于收益，本轮不动。
- **M4｜抢窗时刻与实际发指令时刻解耦**：10 秒窗口 CAS 约束的是「决定触发」时刻，真正指令在子线程网络返回后才发。极端时序下（离开查询卡住 + 10 秒后靠近查询很快）可能出现「先解锁后上锁」乱序、间隔不足 10 秒，且 diagUnlock/diagLock 在决策点就 +1（计的是「尝试次数」非「实际指令数」，展示偏高）。需把 CAS 移到真正发指令前 + 发前再校验窗口，改动面大，留待实机验证。
- **快刷闹钟链死代码**：`startFastRefresh`/`FAST_TICK` 链、`markSmartUnlockDone`/`clearSmartUnlockDone` 标记机制已无调用方（v1.9 引入 CarStateCache 后由缓存快刷窗口取代），注释「10 秒每 2 秒连续刷新」不再兑现。纯清理，不影响功能，本轮不动以免引入风险。
- **熄屏离开阈值固定 90 秒**：用户设置 90~600 秒时，熄屏仍按固定 90 秒，实际是收紧而非注释所称「放宽」。该固定值是用户明确要求（v1.8.2），行为符合预期，仅注释措辞问题。
- 沿用前几轮取舍：10 秒窗口不落盘、无 BLE 去抖/双阈值、goAsync 不迁 FGS、snapshot 原子化后已消除的双锁竞态、冷启动显示上次成功 JSON、token apply 异步、诊断 5 秒节流、签名只拦 401、control 不解析业务码、root MMKV 8 字节头、离开上锁失败不重试（上一轮取舍）。

## 五、结论

第五轮（逻辑与冲突专项）确认 8 项并全部修复，其中 1 项严重安全漏洞（engine 缺失可在行驶中解锁）、1 项对称的盲锁风险、2 项 car 状态边界、2 项切号竞态、2 项显示/回调一致性。核心安全底线「行驶中绝不自动解锁」「绝不盲锁」在此轮得到进一步加固。M3/M4 等状态机时序优化连同理由写入取舍，未擅自改动核心在场/闩锁逻辑。均已编译验证并交付 v1.9.6。
