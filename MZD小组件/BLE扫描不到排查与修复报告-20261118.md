# BLE「扫描不到设备」排查与修复报告

> **【历史归档】** 本报告正文记录的 v1.9.9（宽扫诊断）与 v1.9.10（GATT 占用检测、体检按钮、占用暂停上锁）功能，**均已按用户要求全部回滚**。当前 v1.9.11 不含这些能力；扫不到设备时由用户在系统蓝牙里删除配对即可。正文仅作排障思路存档，不代表现行实现。

日期：2026-11-18　|　**当前交付：v1.9.8 / versionCode 37**

> **状态：v1.9.9 与 v1.9.10 的改动已按用户要求全部回滚。** 用户确认车上 BLE 模块 MAC 固定，且「在系统蓝牙设置里删除配对后就连不上了」——即连接占用由配对引起，用户可自行解除，无需 App 内做 GATT 探测、无需界面按钮。本文保留作诊断记录，其中第七节（v1.9.10 GATT 检测方案）已不体现在当前代码中。
现象：手机蓝牙设置里已经发现并**连接**了该设备，但 App 一直扫描不到（偶发一次，重启 App 后仍无效）。

> **用户已确认：车上的 BLE 模块 MAC 固定不变。** 因此「MAC 轮换(RPA)」这一支被排除，
> 成因锁定为 **设备被 GATT 连接后停止广播**。v1.9.10 据此把「猜」变成了「可见 + 可控」，
> 并顺带修掉一条会**误锁人**的安全隐患（见第七节）。

---

## 一、结论先说

这个现象**有两类完全不同的成因**，必须先分清，否则会白改代码：

| 类别 | 成因 | 能否靠改 App 解决 |
|---|---|---|
| **A. 设备/系统行为** | 设备被连接后**停止发送 BLE 广播**；或该设备只支持经典蓝牙（BR/EDR），根本没有 BLE 广播 | **不能**。App 只被动接收广播，不做连接。只能提示/引导用户断开连接 |
| **B. App 侧缺陷** | 扫描被系统配额限流后静默失败、自愈判定失效、退避被绕过、出错后无任何日志 | **能**，本次修了 |

**主因是 A（已由用户实机确认）**：BLE 外设一旦建立 GATT 连接，多数会停止 advertising，此时任何人（包括系统设置）都只能在"已连接"列表里看到它，但**扫不到它的广播**。本 App 的设计是「只扫描广播、不建立连接」，因此一旦设备处于连接态，它就无从感知。

**判定方法（一句话）**：在 App 里点「扫描并选择附近的 BLE 设备」——这一步用的是**无过滤全量扫描**。
- 如果这一步也扫不到 → 设备没在广播（A 类），去系统蓝牙里断开/取消配对。
- 如果这一步能扫到、但后台自动控车扫不到 → App 过滤匹配问题（B 类），本次已加固。
- v1.9.10 起更省事：点「扫描不到？体检」直接读出「本机是否正连着它」，不用再靠推断。

## 二、本次修复的 App 侧缺陷（8 项）

### 1. 扫描退避被绕过 → 撞系统配额后永久静默失败（最关键）
`BleScanService.startScanInternal()` 原本只判断 `if (scanning) return`。
`onScanFailed` 设置了 10 秒退避，但 `onStartCommand` 每次被调用（切开关、进页面）都直接调 `startScanInternal`，**完全不看退避**。
Android 7+ 限制「30 秒内最多 5 次 startScan」，超了之后 `startScan` **静默失败——不回调 `onScanFailed`**，App 里表现就是"一直扫描不到，且没有任何报错"。
**修**：`startScanInternal` 尊重 `restartAt`；退避期间不再直接 return（那会把扫描停在已停止状态），改为延迟到退避结束后自动启动。

### 2. 自愈判定用错了参照物 → 周边只要有别的 BLE 设备就永不重启
原逻辑：`now - lastResultAt >= 60s` 才重启扫描。但 `lastResultAt` 记录的是**任意** BLE 广播回调，周边有其它 BLE 设备（手环、耳机、邻居的门锁）时它一直在刷新，**目标设备扫不到也永远不会触发重启**，只能干等 5 分钟兜底。
**修**：改用 `noHitSince`（最近一次**命中目标**的时间）。命中目标才清零，且**刻意不随自愈重启清零**——否则每次重启都归零，60 秒判定永远到不了。

### 3. 命中目标后不退出宽扫
宽扫命中后若继续宽扫，会长期全量扫描耗电。
**修**：严格命中即 `main.post` 回主线程恢复定向扫描（不能在 ScanCallback 线程 stopScan 自己，可能死锁）。

### 4. 看门狗自愈重启会顺手清掉「在场」状态
补救分支原本传 `resetState=true`，会把 `present` 清 false。人其实还在车边时，下次命中会被当成"重新靠近"，**绕过解锁闩锁再下发一次解锁指令**。
**修**：该分支改 `resetState=false`。

### 5. `onScanFailed` 不清理注册
失败常是"部分注册成功"的状态，不 `stopScan` 清残留，下次 `startScan` 可能因重复注册直接失败，形成死循环。
**修**：失败分支显式 `stopScan(scanCb)`。

### 6. 宽扫期间零回调不自愈
原判定带 `!wideScan` 前置，宽扫期间即使扫描注册已死也不会重启。
**修**：去掉该前置，宽扫期间零回调同样重启验证。

### 7. 诊断数据只存不刷新 → 主界面永远显示旧计数
`if (diagCb.get() > 0) persistDiag()`：一次回调都没有（真扫不到）时**永远不落盘**，用户看到的是上一次的旧数据，会误判成"服务停了"。
**修**：改为无条件心跳落盘；并新增 `scan_starts`（扫描启动次数）、`restarts`（自愈重启次数）、`wide`（当前是否宽扫）三个字段，主界面诊断区直接显示「扫描：启动 N 次 · 自愈重启 N 次 · 模式 定向/宽扫」。

### 8. 用户没有可操作的恢复手段
**修**：`ACTION_START` 支持 `EXTRA_FORCE`。用户主动「关掉再打开 BLE 开关」或「重新选设备」时强制清旧注册并解除退避——这是撞上系统配额后唯一能让扫描立刻复活的路径。进页面补启服务仍用 `force=false`（否则服务刚起就被 stop 再 start，可能被判重复注册）。

## 三、新增的排障能力（这次重点）

### 3.1 宽扫诊断（仅诊断，绝不参与动作判定）
定向扫描**连续 60 秒零命中**时，临时取消硬件过滤（宽扫）60 秒，把周边广播设备清单写进「指令日志」。
- 每次服务生命周期只给 1 次额度（正常下车也必然零命中，必须限量，否则全量扫描耗电）。
- **宽扫不参与任何解锁/上锁判定**：匹配仍是严格相等（忽略大小写）。
  > 曾经考虑用「名称包含」把 MAC 轮换的设备认回来，但宽扫取消了硬件过滤，子串匹配会把邻居的同品牌车（目标 `Mazda`、邻居 `Mazda CX-30`）误认成目标并解锁——已明确放弃，安全优先。

日志示例：
```
BLE 宽扫周边 5 台：AA:BB:.. Mi Band 7 (-72)；CC:DD:.. Mazda (-58)；…。
若清单里有你的车但 MAC 与已选设备不同，说明设备 MAC 已变化，请回 App 重新扫描选择
```
```
BLE 宽扫：60 秒内周边没有任何 BLE 广播。设备大概率没在广播（已被系统蓝牙连接/配对、
或已断电/休眠），请先在系统蓝牙里「断开 / 取消配对」再试；若周边其它设备也扫不到，
说明扫描被系统限流，需关闭再打开手机蓝牙
```

### 3.2 常驻通知新增「命中」行
`命中：N 秒前` / `命中：本次启动后一次都没命中`。配合诊断区的「回调 / 命中」计数，可以直接区分：
- 回调 = 0 → 设备没广播，或扫描被限流（真扫不到）
- 回调 > 0、命中 = 0 → 广播正常但过滤器/名称不匹配（App 侧）
- 命中 > 0、弱信号 > 0 → 能扫到但信号不到阈值（走远了，不是故障）

### 3.3 主界面文案
BLE 设置区新增红字提示：**扫描不到设备？先在系统蓝牙里「断开 / 取消配对」该设备——很多设备被连接后会停止 BLE 广播，而本 App 只需要广播、不需要连接。**

## 四、遇到扫不到时的操作顺序（v1.9.10 更新）

1. **点「扫描不到？体检 / 查看设备占用」**：一眼看清本机是否正连着它、是否已配对。
   - 显示「已连接（GATT）」→ 点「打开系统蓝牙设置」，对该设备「取消配对 / 忘记此设备」。
     回到 App 后无需手动重启扫描：服务在数秒内检测到连接解除，会**自动**重建扫描。
   - 显示「未检测到 GATT 连接」→ 看下一步。
2. 点「扫描并选择附近的 BLE 设备」做全量扫描（不带任何过滤）。
   - 能列出周边设备但没有本车 → 设备没在广播（多半被另一台手机占用、模块休眠或断电）。
   - 一台都没有 → 扫描被系统限流：关闭再打开手机蓝牙，等 10 秒重试。
   - 列出了本车 → 重新选一次即可（正常情况下 MAC 不会变，选完就能恢复）。
3. 仍不行：打开「查看指令日志」，看是「周边没有任何 BLE 广播」还是「周边 N 台但没你的车」。
4. 期间注意：**设备被连接时自动上锁已暂停**（防止把车里的人锁住），请手动确认车辆已锁。

## 五、已知取舍（未改）

- **设备处于连接态时停止广播，App 无法绕过**。这是 BLE 协议与设备固件行为，不是 App bug。App 不做连接、只收广播，因此只能在 UI 与日志里明确提示，不能自动"抢"连接。
  - v1.9.10 补充：系统里**没有公开 API** 能让第三方 App 断开别人的 GATT 连接——`BluetoothDevice.removeBond()` 是 `@SystemApi` 隐藏方法（编译期就不可见），反射在 Android 9+ 非 SDK 接口限制下对 targetSdk 34 基本被拦。所以「解除占用」只能引导到系统蓝牙设置页由用户操作，App 负责**检测、告知、并在检测到解除后立刻自愈**。
- **`neverForLocation` 保留**：移除会新增定位权限与合规成本；且它主要影响 iBeacon/定位类广播，普通 BLE 外设不受影响。若后续证实有设备因此被过滤，再单独评估。
- **宽扫额度固定 1 次/服务生命周期**：宁可排障信息少一点，也不做常态全量扫描（耗电）。v1.9.10 起设备处于占用态时**直接跳过宽扫**（必然零命中，纯耗电）。
- **`CarStateCache` 的每轮车况日志仍只写 logcat**：每 3 秒一条会把指令日志刷没，噪音大于价值；失败与异常类日志仍会经 `CarActions` 进入弹窗。
- **指令日志弹窗**：固定占屏 60%，不随滚动隐藏（用户明确要求按钮放底部）；鸿蒙/部分 ROM 的 ScrollView 滚动行为未实机验证。
- **占用探测的可见范围有限**：`getConnectedDevices(GATT)` 只能看到**本机**的连接。设备被另一台手机（家人手机上的控车 App）连走时，本机检测不到——这种情况仍需靠「全量扫描能收到邻居设备、却收不到本车」来判定。

## 七、v1.9.10 追补：成因锁定后，把「猜」变成「可见 + 可控」

前提确认：**设备 MAC 固定不变**。于是：
- 定向 MAC 过滤本身没问题，宽扫不再是排查主力（仅在被限流等极端场景留作对照）。
- 「扫不到」= 设备没在广播 = 极大概率被 GATT 连接占用（系统蓝牙设置里显示"已连接"正是这个状态）。

### 7.1 新增：GATT 占用实时探测（`BleGatt.java`）
用 `BluetoothManager.getConnectedDevices(BluetoothProfile.GATT / GATT_SERVER)` 读系统全局连接表（需 `BLUETOOTH_CONNECT`，已声明），把目标 MAC 是否处于连接态变成可读状态：
- 每 5 秒探测一次（看门狗 2 秒节拍下实际约 6 秒），纯只读，**绝不发起连接**（本 App 绝不连接设备，避免自己制造停播）。
- 命中 → 通知标题变为「设备被连接」、正文加「设备被连接停播」、大文本新增「占用」行并给出唯一有效动作；诊断落盘新增 `gatt` 字段，主界面显示「设备占用 是（已被连接，停播）/ 否」。
- 占用解除 → **立即** `restartScan`（不等 5 分钟兜底、不等 60 秒零命中判定），并把 `lastSeen/screenOnAt` 重置为当前时间，给「重新发现目标」留宽限。实测语义上等价于用户点一次「重启扫描」，但全自动。

### 7.2 新增安全修复：占用期间**禁止**自动上锁（重要）
这是本次复盘的意外收获，属于会伤人的真问题：

> 设备被连接 → 停止广播 → App 一直扫不到 → 看门狗按「静默超时」判离开 → `onBleAbsent` 查到 `unlocked==true && started==false` → **下发上锁**。
> 而此时人可能就在车里（熄火休息、后排有人、刚上车间没启动），会**被锁在车内**。

原有防线只覆盖「车况查询失败」「发动机已启动」两种情况，无法识别「扫描本身失效」。v1.9.10 在离开判定前先看 `gattBusy`：
```java
if (gone) {
    if (gattBusy) { /* 只写日志与诊断，禁止上锁 */ }
    else if (tryClaimActionWindow(now)) { /* 原上锁流程 */ }
}
```
取舍：占用期间宁可**漏锁**（用户在车旁，通常自己会锁或事后手动锁）也不**误锁**（人在车内是安全事件）。通知与大文本里持续提示「请手动确认车辆已锁」，不会让用户误以为已锁。

### 7.3 新增：主界面「扫描不到？体检 / 查看设备占用」
位置：BLE 设置区，「扫描并选择附近的 BLE 设备」下方。一次点击给出：
- 本机连接状态（已连接 GATT / 未检测到）、配对状态、自动控车开关、最近诊断三行；
- 按状态给结论与下一步：**已连接** → 引导到系统蓝牙设置「取消配对/忘记此设备」；**已配对未连接** → 列出「被另一台手机占用 / 模块休眠 / 扫描被限流」三种可能；**未配对未连接** → 说明设备根本没在广播，与 App 无关；
- 按钮：`打开系统蓝牙设置`（`Settings.ACTION_BLUETOOTH_SETTINGS`，公开 API，100% 可靠）/ `仅重启扫描`（`EXTRA_FORCE` 强制重建）。
- 回到主界面（`onResume`）自动刷新诊断，方便「去设置断开 → 回来看是否恢复」的对照。

### 7.4 新增：选设备全量扫描的提示精确化
原实现把两种截然不同的情况混在一句话里。现区分：
- **一台设备都没收到** → 扫描被限流/蓝牙异常（不是目标设备的问题），提示关开蓝牙或重启手机；
- **收到周边设备但没有目标** → 才是「目标停播」的可靠证据，并附带「本机是否正连着它」，直接指向处理动作。

### 7.5 顺带修复：关键节点落盘被 5 秒节流吞掉
`persistDiag()` 有 5 秒节流，解锁/上锁/扫描失败/占用翻转这些关键节点可能被丢弃，主界面看到的诊断会**落后一个状态**，排查时容易误判"动作没发生"。新增 `persistDiagNow()`（清节流戳后立即写），上述节点全部改用它。
