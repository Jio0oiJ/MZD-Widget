## 一、严重问题（本次新发现，与被否决的 v1.9.11 修复无关）

### S1. `RootTokenReader.runSu` 超时保护失效，su 授权弹窗不确认会永久挂死后台线程
- **位置**：`RootTokenReader.java:238-259`，核心 `:246-250`
- **事实**：`readAll(p.getInputStream())`（:246）是阻塞读，直到 su 进程关闭 stdout 才返回；而 30 秒超时判断放在其后的 `waitFor(30, ...)`（:250）。注释（:248-249）声称"避免 su 授权不确认导致永久阻塞"，但阻塞实际发生在 `readAll`，`waitFor` 永远执行不到，`finally` 的 `destroyForcibly()`（:257）也到不了。
- **后果**：Root 导入/静默解锁初始化线程永久卡住；若上层先 `setBusy(true)`，按钮永久禁用，与注释意图完全相反。
- **建议**：把读流纳入超时控制。用 `Future.get(30s)` 包住读流，超时后 `p.destroyForcibly()` 强制关闭以解除 `read()` 阻塞；stdout/stderr 用 `redirectErrorStream(true)` 合并为单流读，避免 stderr 填满管道死锁。
- **备注**：这是本次审核最确定的实质性 bug，且与 BLE/GATT/体检等被否决方向无关。

### S2. 一键启动步骤1把 `unlocked==null`（未知）当作"未锁"下发锁车指令
- **位置**：`CarActions.java:120-130`、`:242-244`、`:259-261`
- **事实**：`statusUnavailable`（:259-261）只在 `started==null && unlocked==null`（两者全缺）时才判不可用。若车况是 `started=false, unlocked=null`（字段部分缺失），会通过 `queryWithRetry` 被当成"可用"（:196）。随后 `isLocked()`（:242-244）对 `unlocked==null` 返回 `false`，:128 的 else 分支把"未知"当成"未锁"，:130 直接下发 lock。
- **后果**：`unlocked` 持续缺失时，`poll(isLocked)` 永不命中，按 `SMART_LOCK_MAX_RETRY=2` 重发，累计可发 **3 次 lock**；`started=true, unlocked=null` 时也会误发 lock。这违反你反复强调的"null 不能当未启动/未锁下发动作"底线。
- **建议**：在 :126 前加显式守卫，`s0.unlocked==null` 时终止并 `cb.onResult(false, ...)`，不下发任何指令。步骤2/3 的 poll 用 `Boolean.TRUE/FALSE.equals` 已正确处理 null，无需改。
- **备注**：此项与被否决的 v1.9.11「engine/lock 异常类型校验」不是同一处——那是 Api 解析层，这是 CarActions 判定层，v1.9.11 未修此处。BLE 自动路径（`onBlePresent/onBleAbsent`）的 started/unlocked null 守卫已核查正确（:298-302、:382-385），不受此项影响。

## 二、中低问题（本次新发现）

### BLE 与扫描（BleScanService / BleBootReceiver / Prefs）
- **M1（中）**：蓝牙关→开时看门狗走 `startScanInternal(true)`（`:338`），`resetState=true` 会 `setPresent(false)`（`:457-459`），与 :284-286"蓝牙关→开不能重置 present"的设计注释直接矛盾。后果：停在旁边的设备被重开蓝牙后可能重复触发靠近判定（有车况"已解锁跳过"兜底，未定严重）。建议：仅"设备被重新选择（filterKey 变化）"才 resetState=true，蓝牙恢复/失败重试一律 false。
- **M2（中）**：`restartAt` 退避闸门只在看门狗 `:336` 检查，`onStartCommand`（`:288-292`）直接 `startScanInternal(false)` 不检查。Activity 每次进入都发 ACTION_START，可能在扫描失败退避期内插队 startScan，逼近"30 秒 5 次"配额。建议：把 `now >= restartAt` 检查下沉到 `startScanInternal()` 开头统一判断。
- **M3（中）**：`onScanFailed`（`:183-195`）只置 `scanning=false` 并设退避，未调 `stopScanInternal()` 清残留注册。`SCAN_FAILED_ALREADY_STARTED` 时旧注册仍回调。建议：onScanFailed 内直接 stopScanInternal()。
- L1（低）`onScanResult`（:132-180）无 try/catch；L2（低）`startScan` 与 `scanning=true`（:449-450）间竞态可吞掉失败；L3（低）看门狗每约 5 秒主线程同步 commit 诊断（:347→Prefs:177）；L4（低）阈值 getter 无防御性 clamp；L6（低）诊断时长未处理系统时间回拨（Prefs:187-190）。

### 控制状态机（CarActions）
- **M1（中）**：一键启动 `SMART_RUNNING`（:113）只防自身重入；BLE 自动/手动按钮入口不检查它，无跨入口互斥。一键启动等待确认期间，BLE 判离开可能发 lock（:387），导致指令冲突。建议：暴露 `isSmartRunning()` 让 BLE 回调期间跳过待重试。
- **M2（中）**：10 秒 CAS 窗口抢占时刻（BleScanService:159/361）与实际发指令时刻（CarActions:324/387）解耦——抢窗后 `refreshAndWait` 等数秒才发指令。极端调度下两条 BLE 指令实际间隔可低至约 1 秒（已知 M4 取舍，本次确认属实）。
- **M3（中）**：`poll` 内 `queryWithRetry` 两轮查询失败即 `return null`（:217-220），即使指令已发出、只是确认丢失，也会终止流程。偏保守但削弱"确认式状态机"目标。
- **M4（中）**：`queryWithRetry` 单次最坏约 40 秒（20s×2），超过 poll 单轮 20/30 秒窗口（:212-216），重发节拍被拉长，可能漏看 10 秒台阶上报的状态更新。
- L1（低）`onBleAbsent` 车况不可用返回 `ok=true` 与 `onBlePresent` 的 `ok=false` 语义不对称（:370-372）；L2（低）`cb.onResult(true)` 抛异常会被 catch 后二次回调失败（:163-166）。
- 观察项：步骤3在 `started==true` 下发 unlock（:153）是用户显式一键启动的设计意图（BLE 自动路径已守 started==true 不开门），建议补注释避免后续误判。

### 缓存 / 网络 / 凭证（CarStateCache / Api / CredFile / RootTokenReader）
- **中**：`getStatus`（Api:123-156）永不返回 null，`{"status":0,"data":{}}` 会被包装成全空 CarState，CarStateCache `ok=(s!=null)`（:214）判成功并用它覆盖有效缓存，丢失上次真实车况。建议：未取到任何有效字段时返回 null，或 queryOnce 增加 `if(s.started==null && s.unlocked==null) ok=false`。
- **中**：`checkBusinessError`（Api:216-228）只解析 401，其它业务失败码（如 `status=400 车辆离线，指令未下发`）被当成功，control() 尤其危险——指令实际失败却记为成功。建议：定义成功码集合（0/200），其它统一抛异常带 message。
- **中**：`app` 字段非 volatile 且锁外读写（CarStateCache:33/64/195），工作线程可能长期读不到后续设置的 Context，导致桌面快刷不更新。建议：`private volatile Context app;`。
- **中**：CredFile 先 `deleteOld`（:55）再 `insert`（:61），写入失败时旧凭证已删；RELATIVE_PATH selection 带尾斜杠（:107）与 insert 值（:59）不一致可能删不掉旧记录。建议：用 IS_PENDING 事务语义，selection 字符串与 insert 完全一致。
- 低：CredFile 直写非原子（:87-89）；Api.readAll 异常路径不关流（:312-320）；RootTokenReader marker/varint 边界依赖异常兜底（:179/198-208）；GET/POST 签名规则差异需抓包确认（:164-184 vs :230-284）。
- **已核查无问题**：epoch 同临界区快照（CarStateCache:199-205）、invalidate 丢弃在途结果（:155-163/225-240）、reqSeq/doneSeq/successSeq 等待者无挂死/假唤醒、snapshotWithError 原子同取（:135-139）、MIN_GAP/快刷语义（:166-191）、NULL 防护（Api:137-138/148-152）、401 双路径覆盖、RootTokenReader 命令注入白名单（:122）、JSONObject.NULL 陷阱。

## 四、总体结论

1. **BLE 自动控车安全主线守得住**：`onBlePresent/onBleAbsent` 对 `started==true`、`started==null`、`unlocked!=true`、车况不可用均有保守拦截，闩锁与上锁路径正确，未发现可直接导致"行驶中自动开门"的致命漏洞。
2. **缓存与防切号机制自洽**：epoch 代次、等待者机制、snapshotWithError 原子同取经逐场景推演无挂死/冒充问题。
3. **本轮真正值得关注的新问题**：
   - **S1**（RootTokenReader 超时失效）最直接、最确定，且与任何被否决方向无关；
   - **S2**（一键启动步骤1把 null 当未锁下发 lock）触及你反复强调的安全底线，但位于 v1.9.11 未覆盖的判定层；
   - 其次为 BLE 的 M1/M2/M3 状态机一致性与配额退避严谨性。
4. 第四节之外的中低项多为健壮性/性能细节，可按版本节奏处理，不影响核心控车正确性。

**未做任何修改。** 如需修复，请明确指定要处理哪些编号（例如"修 S1、S2"或"只修 S1"），我会按最小改动实施、重新构建并单独备份版本。
