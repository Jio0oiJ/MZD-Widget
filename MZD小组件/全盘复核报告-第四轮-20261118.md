# MZD 第三方控车客户端 · 第四轮全盘复核报告

日期：2026-11-18
版本：v1.9.4（code33）→ **v1.9.5（code34）**
权威源码：`mzdwidget_build/app/src/main/java/com/example/mzdwidget/`

## 一、本轮方式

三路只读审查 Agent 并行（BLE 层 / 支撑层 / 显示广播层），再由主审逐条核实代码事实后决定修复，最后 clean 重建 + 版本/签名核验 + 覆盖交付 APK。全程未质疑前几轮已定架构与安全底线。

## 二、确认并已修复的问题（6 项）

### 1【高·BLE 服务静默停摆】API 31+ 权限校验漏项 + isEnabled 无保护 + 看门狗异常不自愈
- `BleScanService.hasPermission()` 在 SDK≥31 只校验 `BLUETOOTH_SCAN`，漏 `BLUETOOTH_CONNECT`。而 `MainActivity.hasBtPermission()` 两者都查、且部分授权时「不改 Prefs、不动开关」——于是「给了 SCAN、拒了 CONNECT」时服务照常被拉起。
- `adapter.isEnabled()` 三处调用（`onStartCommand`、看门狗 `run()`、`startScanInternal`）均无 try-catch，API 31+ 下受 `BLUETOOTH_CONNECT` 保护，缺权限抛 `SecurityException`。
- 最严重：异常从看门狗 `run()` 逃逸后，末尾的 `main.postDelayed(this, WATCHDOG_MS)` 不执行 → 唯一驱动循环永久终止，判离开/上锁、扫描自愈、诊断落盘、通知刷新全部停摆且不自愈。
- **修复**：`hasPermission()` 同时校验 SCAN+CONNECT；新增 `isBtOn()` 统一包 try-catch(SecurityException)，三处改用之；看门狗 `run()` 用 `try/catch/finally` 包裹，把循环体抽成 `watchdogTick()`，`postDelayed` 放 finally 保证必定自调度。

### 2【中·安全底线】lock 子字段全缺被误判「已锁」
- `Api.getStatus()` 中 `lock` 对象存在但 `lf/lr/rf/rr` 全缺（服务端降级/部分响应）时，`anyEqualsOne` 四个 `optInt` 全取默认 0 → `false`（明确「已锁」，非 null），绕过 `CarActions.statusUnavailable()` 的「字段全缺=不可用」保护，可能凭不可靠状态下发解锁。
- **修复**：仅当 `lock` 至少一个门字段真实存在时才写 `s.unlocked`，否则保持 null，交给上层按不可用处理。

### 3【中·安全底线】切号竞态：在途旧查询把旧车况写回桌面
- `CarStateCache.invalidate()` 只清内存 cached/lastError，但已发出、仍在飞行中的 `/car/status` 用旧 token 返回后会写回 cached 并 `onGlobalStatus` 写盘 → 上账号/上辆车的车况冒充新账号实时状态。
- **修复**：引入 `volatile long epoch` 代次。`invalidate()` 递增 epoch；`queryOnce()` 记录发起时 epoch，完成时若已变则丢弃本轮结果（不写缓存、不写盘、successSeq 不推进，但推进 doneSeq 避免等待者超时，`refreshAndWait` 按「未确认」返回 null）。

### 4【中·显示错误】切号后凭证来源永远显示「账号登录」
- `Prefs.save()`（账号登录）写 `password`，`saveToken()`（Root/手动 Token）不清理 → 账号登录后再切 Token，`refreshStatusText()` 读 password 非空，永远显示「账号登录」。
- **修复**：`saveToken()` 清空 `password/phone/userid`；Root 导入在其后单独补写 userid，故「Root 读取」展示不受影响；手动 Token 展示为「手动 Token」。

### 5【低·资源泄漏】CredFile MediaStore 输出流未关闭
- `os.write()` 抛异常时 `os.close()` 不执行，泄漏 fd；且 `IS_PENDING=0` 复位被跳过，留下永久不可见的脏记录。
- **修复**：try-with-resources 包裹输出流，`IS_PENDING` 复位移入 finally。

### 6【低·并发/输入跳变】
- `MainActivity.picked`（设备扫描结果）由 binder 线程写、主线程读/clear，原 `LinkedHashMap` 无同步 → 改 `ConcurrentHashMap`。
- RSSI 阈值 / 离开秒数输入框 `afterTextChanged` 每次击键都解析+clamp 落盘（如输入 "-7" 被 clamp 成 -30），阈值随击键瞬时跳变 → 改为仅当输入值落在合法范围（RSSI -100~-30、离开 10~600）时才落盘，中间态保留旧值。

## 三、未改的取舍（需实机或拍板，本轮不动）

- **离开上锁失败/车况不可用跳过后不自动重试**：判离开时 `setPresent(false)`，看门狗进入判定的前置条件 `if (present && ...)` 不再满足，故 `onBleAbsent` 不会再被调用。若判离开那一刻网络抖动或车况不可用，车可能一直不锁，无自愈（除非再次靠近→离开）。这涉及新增有界重试状态机 + 复用 10 秒窗口 + diagLock 计数口径，改动面较大；且「车况不可用跳过」是既定安全策略（绝不盲锁），是否重试上锁需产品确认。与主审核对后列为取舍，未改代码。
- **诊断计数口径**：`diagUnlock/diagLock` 在「决定触发」时就 +1，而实际可能因车况不可用/确定性跳过未真正发指令，数字计的是「尝试次数」而非「实际指令数」，展示偏高。不影响控主逻辑。
- 沿用前几轮取舍：10 秒窗口不落盘（已 CAS 防并发）、无 BLE 去抖/双阈值滞回、goAsync 承载长任务不迁 FGS、snapshot/lastError 双锁窄竞态、冷启动显示上次成功 JSON、token apply 异步落盘、诊断 5 秒节流、签名只拦 status==401、control 不解析业务码、root 凭证 MMKV 8 字节头解析脆弱。
