# 服务器 /car/status 刷新间隔与指令状态回显延迟实测报告

测试日期：2026-11-18　|　查询接口：`GET https://iov.edaoduo.com/aoduo/prod/api/v2/car/status?carid=<车辆ID>`　|　控制接口：`POST /car/ctrl`

> 本文分两部分：**第一部分**为查询接口的最短刷新间隔（不改变车辆状态）；**第二部分**为发送解锁/上锁指令后，车况多久才反映出状态变化（真实控车，测试后已恢复上锁）。

## 一、结论先行

**服务器对 `/car/status` 查询没有硬性频率限制（无 429、无限流业务码、无封 IP）。**

在累计 100+ 次真实请求、横跨从「0 间隔突发」到「16 路并发」的所有频率档位下，**全部返回 HTTP 200 + `status=200`，零次被拒**。因此从"服务器允许"的角度，没有测出可用下限——它不拒绝高频查询。

但实测揭示了两个真正决定"合理刷新间隔"的因素：

1. **回源耗时约 1.17 秒**：服务器并非每次都即时返回。约 60~70% 的请求耗时稳定在 **1.14~1.22s**（服务器回源到车厂 T-Box 拉实时数据），约 30~40% 耗时 **0.13~0.22s**（命中服务器本地缓存）。二者随机分布，不是固定周期。
2. **车况数据本身更新很慢**：整个测试期间（约 3 分钟、100+ 次查询），返回的 `time` 字段（车辆上报时间戳）与车况内容 hash **始终不变**（车静止）。即短时间内重复查询拿到的是**同一份数据**。

**实用结论**：服务器"允许"的最快可以压到 1 秒以内乃至并发；但"有意义"的刷新没有那么快——数据本身几分钟才变一次，且慢响应要 1.17s。当前 App 采用的 **3 秒 MIN_GAP 是保守且合理的**：既远低于服务器承受力，又避免无谓高频轮询。若想更快，1 秒也完全不会被服务器拒绝，只是多数时候拿到的还是同一份车况。

## 二、测试方法

- 完整复刻官方 App 协议：`timestamp`（秒）+ `nonce`（`aod12346`+随机）+ `signature`（`carid`/`nonce`/`timestamp` 字典序拼接后追加 token 取 MD5 小写）+ `apiver=v3` + `X-App-Identifier=0001080002000426082001` + `token`。
- 凭证来源：用户提供的共享凭证文件 `mzdcred.jpg`，经 `AES/CBC/PKCS7Padding`（密钥 `MZD2026CredKey01` / IV `MZD2026CredIV001`）解密得到 `MZD1\n<token>\n<carid>`。（token 不写入本报告。）
- 基线验证：新 token 返回完整车况 `status=200`，含 engine/lock/door/gps/mileage/oil 等字段；旧 token（2026-11-17 从 data 包提取）已失效返回 401。

## 三、逐档测试记录

| 档位 | 请求数 | 间隔 | HTTP/业务码 | 异常 | 耗时特征 |
|---|---|---|---|---|---|
| 突发无间隔 | 8 | 0s | 200 / 200 | 0 | 1.16s 与 0.17s 交替 |
| 1 秒间隔 | 6 | 1.0s | 200 / 200 | 0 | 快慢随机 |
| 2 秒间隔 | 5 | 2.0s | 200 / 200 | 0 | 几乎全慢 ~1.16s |
| 3 秒间隔 | 4 | 3.0s | 200 / 200 | 0 | 快慢随机 |
| 1 秒密集 | 40 | 1.0s | 200 / 200 | 0 | 快 15 次(均 0.175s) / 慢 25 次(均 1.170s) |
| 0.3 秒间隔 | 20 | 0.3s | 200 / 200 | 0 | 快慢随机 |
| **16 路并发** | 16 | 同时 | 200 / 200 | 0 | **全部 1.22s 内完成** |
| 0.1 秒间隔 | 30 | 0.1s* | 200 / 200 | 0 | 实际被慢响应拉长到 ~1.03s |

\* 串行请求下，0.1s/0.3s 的目标间隔会被单次回源的 1.17s 覆盖；真正的并发能力由 16 路并发那轮验证。

**车况稳定性校验**：1 秒密集 40 次期间，去掉 `time` 字段后的车况 JSON hash 只有 1 个值（`2ba3871a`），`time` 只有 1 个值（`1794994597`）——证明车的静止状态下，高频查询拿到的完全是同一份数据。

## 四、快慢双峰的解释

耗时呈双峰而非固定缓存周期（相邻慢请求间隔 2.1~5.7s 完全随机），最合理的解释是服务端**两级路径**：

- **~1.17s（慢）**：缓存未命中，服务器同步回源车厂接口拉取车辆实时状态；
- **~0.17s（快）**：服务端近期已有缓存，直接返回；

两条路径返回的数据内容完全一致（同一 hash）。因此快慢只影响响应延迟，不影响数据新鲜度判断。

## 五、对 App 的建议（供参考，未改动代码）

1. 现行 `CarStateCache` 的 **3 秒 MIN_GAP + 标准 10 分钟 + 触发快刷 20 秒/3 秒** 设计无需因"怕服务器限流"而收紧——服务器根本不限流。
2. 若产品希望触发后车况更新更快，可把快刷间隔从 3 秒下调到 1 秒，服务器完全能承受；但收益有限（数据本身更新慢，1 秒回源还要 1.17s），维持 3 秒更省流量与电量。
3. 真正该关注的不是"服务器拒绝频率"，而是"回源延迟 ~1.17s"：`refreshAndWait()` 的等待超时需留足 >1.2s 余量，否则慢路径下会误判为查询失败。

## 六、测试脚本留档（第一部分）

`re_work/probe_status.py`（单次请求 + 签名）、`probe_real.py`（梯度）、`probe_dense.py`（1 秒密集）、`probe_limit.py`（并发/极限）、`DecryptCred.java`（凭证解密）。脚本中的 token 为临时测试值，未提交任何版本库。

# 第二部分：解锁/上锁指令 → 车况状态变化延迟

## 七、结论先行

**发指令后，车况 `lock` 字段约 6~8 秒才反映变化**（服务器 `POST /car/ctrl` 本身 1.2s 内就回 `status=200 请求已接受`，但那只是"指令已收",不代表车已执行；真正的状态变化要等车辆上报）。

| 操作 | 首次实测 | 重复 4 轮 | 平均 | 变化区间 |
|---|---|---|---|---|
| 解锁 unlock | 6.90s | 5.44 / 7.38 / 8.41 / 7.76 | **7.25s** | 约 5.4~8.4s |
| 上锁 lock | 6.35s | 7.09 / 6.79 / 6.67 / 6.44 | **6.75s** | 约 6.4~7.1s |

指令 HTTP 响应：全部 `HTTP 200 + {"message":"请求已接受！","unit_test":"success","status":200}`，耗时 1.19~1.22s。

## 八、关键机制：车况按 ~10 秒周期上报

测试中发现车况的 `time` 字段（车辆上报时间戳）在指令后发生**台阶式跳变**，而非平滑变化：

```
静止基线 5010 →(解锁)→ 5030 → 5038 →(解锁)→ 5050 → 5059 →(解锁)→ 5071 → 5081 →(解锁)→ 5092 → 5101
```

相邻上报间隔约 **8~12 秒**（平均 ~10s）。指令延迟的本质是：**指令秒级送达 → 车执行 → 等下一个 ~10s 上报周期把新状态带回服务器 → 再叠加 1.17s 回源查询延迟**。这解释了为何延迟稳定落在 6~8s 而非更短。

## 九、对 App 一键启动状态机的重要影响

1. **poll 轮询间隔需 ≥ 变化延迟**：`CarActions` 一键启动的 `poll()` 若用 3 秒间隔去确认 lock/started 变化，可能连查两三轮都还是旧值——必须能容忍至少 ~8~10s 才确认。当前 `refreshAndWait()` 触发快刷窗口 20s/3s 一轮，理论上够覆盖，但要确认等待超时 >1.2s（回源慢路径）。

2. **`boot_time` / 轮询超时勿设太短**：发指令后若 <6s 就判定"指令失败"，会误判——车的真实执行+上报至少要 6~8s。

3. **手动按钮触发快刷 20s 窗口是够的**：20s ≈ 2 个上报周期，覆盖状态回显没问题；若缩到 10s 以内则可能漏掉变化。

## 十、测试方法与安全

- 控制协议：`POST /car/ctrl`，body `carid=<carid>&ctrl=unlock|lock`，签名仅含 `nonce`/`timestamp` 两项排序拼接（**与 GET 不同，不含 body 参数**）+ token，MD5 小写；公共头同查询。
- 每秒轮询一次 `/car/status`，以 `lock.{lf,lr,rf,rr}` 任一为 1 判定"已解锁"、全 0 判定"已上锁"。
- **安全兜底**：脚本用 `try/finally`，每轮结束及整个测试结束时均检查并强制上锁。测试全程发动机 `engine=0`（熄火），最终车况 `unlocked=False`（已上锁）。
- 脚本：`re_work/probe_ctrl.py`（单次完整流程）、`probe_ctrl_repeat.py`（4 轮统计）。token 未写入报告。

# 第三部分：依据实测调整 App 时间间隔（v1.9.7）

## 十一、调整原则

实测给出的四个锚点：**状态回显 6~8s（峰值 8.4s）· 车况约 10s 台阶上报 · 回源约 1.17s · 服务器不限流**。逐一核对全工程时间常量后，只有**直接依赖"发指令后等多久才确认状态"**的间隔需要动；其余与状态回显无关或已有充足余量的，一律不动——避免碰已反复论证过的状态机。

## 十二、逐项决策

| 常量 | 位置 | 原值 | 实测对照 | 决策 |
|---|---|---|---|---|
| `SMART_UNLOCK_RETRY_MS` | CarActions 步骤3 | 15s | 解锁回显峰值 8.4s + 查询开销，叠加 10s 台阶上报可能错过一个周期 | **15s → 20s** |
| 轮询注释 | CarActions | "每2秒" | 代码一直是 `SMART_POLL_MS=3000` | **注释改为3秒** |
| 兜底注释 | CarWidget | "晚于15秒解锁" | 18s 兜底自 v1.8 起已停用、无调用点 | 注释标注已停用 |
| `WAIT_TIMEOUT_MS` | CarStateCache | 20s | 最慢回源 1.2s；双查询约 8.4s | 保留（余量充足） |
| `MIN_GAP_MS` / `FAST_MS` | CarStateCache | 3s | 不限流；3s 查询已能覆盖 10s 上报周期 | 保留 |
| `SMART_LOCK_RETRY_MS` | CarActions 步骤1 | 20s | 上锁回显 6.75s | 保留 |
| `SMART_START_RETRY_MS` | CarActions 步骤2 | 30s | 启动为机械动作，无实测但 30s 保守 | 保留 |
| `DEDUP_MS` | BleScanService | 10s | 与状态回显无关，已 > 8s | 保留 |
| 离开阈值 | BleScanService | 亮30/熄90s | 远大于回显延迟 | 保留 |
| `STANDARD_MS` | CarStateCache | 10min | 省电优先，桌面另有 5min 刷新闹钟 | 保留 |

## 十三、为什么只改解锁窗口

步骤3解锁的 15s 重发窗口，本意是"发 unlock 后若 15s 内车况没变成已解锁，就重发一次"。但实测显示：解锁状态回显平均 7.25s、峰值 8.4s，且车况是约 10s 台阶上报的。若恰好错过一个上报台阶，下一次有变化的数据要到 ~18s 才出现——此时 15s 窗口已过，App 会误判"解锁指令没生效"并重发 unlock。虽然重复解锁本身幂等无害，但会拖长流程、误导日志、且在极端时序下可能与后续动作叠加。放宽到 20s（与步骤1、桌面快刷窗口一致）即可覆盖两个上报周期，留足余量。

步骤1预锁车（20s）和步骤2启动（30s）的窗口本就 ≥20s，实测的上锁回显 6.75s 远在其内，无需改动。
