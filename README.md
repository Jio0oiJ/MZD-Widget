# MZD 控车小组件 · 实验分支：系统扫描全权

> ⚠️ 这是 **experiment/system-scan-only** 实验分支，**不是正式版**。
> 正式稳定版在 [master 分支 / v1.8](https://github.com/Jio0oiJ/MZD-Widget)。
> 实验目的：验证「系统级扫描能否独自承担亮屏 + 熄屏的全部 BLE 控车」，从而砍掉前台连续扫描。

## 这个分支在验证什么

master（v1.8）是**双轨**：

- 前台服务连续扫描（`ScanCallback`，`LOW_LATENCY`）→ 负责实时 RSSI、亮屏/熄屏阈值判「离开」；
- 系统级 `PendingIntent` 扫描 → 只负责熄屏「靠近唤醒」。

本实验版改成**单轨**——只保留系统级扫描：

| | master v1.8 | 本实验版 |
|---|---|---|
| 靠近解锁 | 双通道 | 仅系统扫描 `FIRST_MATCH` |
| 离开上锁 | 前台连续扫描判阈值 | 仅系统扫描 `MATCH_LOST` |
| 实时 RSSI | 有（连续回调） | 仅命中瞬间一次 |
| 扫描注册持有者 | App 进程 + 系统 | 仅系统蓝牙栈 |
| 进程冻结影响 | 连续扫描会失效 | 不受影响（系统解冻投递） |
| 离开时机精度 | 用户可调 30 秒阈值 | 系统迟滞算法决定，不可调 |

**如果实测可行**：更省电、更简单、彻底不受 MIUI 冻结进程影响。
**代价**：离开上锁的时机由系统 `MATCH_LOST` 迟滞决定，可能比预期晚，且无连续信号强度。

## 安装与验证

1. 覆盖安装本实验包（设置里允许未知来源、给通知/蓝牙/定位/后台权限，关闭电池优化）。
2. 主界面扫描选择目标 BLE 设备，打开 BLE 自动控车开关。
3. 看通知栏，应显示「模式：系统扫描全权（亮屏/熄屏同一通道）」「系统唤醒：已注册」。
4. **亮屏测**：走远（离开上锁）、走回（靠近解锁），观察触发时机。
5. **熄屏测**：锁屏后走远再走回，看解锁是否还能触发、上锁是否延迟。

重点观察通知栏这几行：`状态`、`最近命中`、`系统唤醒`、`离开判定（系统 MATCH_LOST）`。

## 已保留的安全护栏

- **10 秒窗口**：解锁/上锁共用，落盘保存，跨进程可靠；系统扫描是边沿事件（只投递一次），撞窗口时挂起、由看门狗在窗口结束后补发，不丢动作。
- **解锁闩锁**：本次靠近只解锁一次，直到离开发出锁车命令/确认已锁才复位。
- **上锁幂等**：先查车况，发动机已启动保持现状、已锁跳过。
- **防降级**：系统扫描每 5 分钟重建一次，对抗 30 分钟后的 opportunistic 降级。
- **蓝牙关→开**：自动重注册并给退避，避免撞系统「30 秒 5 次」配额。
- 一键启动+解锁时序、桌面按钮逻辑与正式版完全一致。

## 已知风险（正是要实测的点）

- `MATCH_LOST` 由系统迟滞算法决定，密集环境短暂漏扫可能误判离开→误上锁，也可能比实际离开晚很多。
- 无连续 RSSI，通知栏信号只在命中瞬间更新一次。
- MIUI 对 `PendingIntent` 扫描的实际投递行为需真机验证（不同 MIUI 版本可能有差异）。

如果实测出现误上锁/不解锁，说明单轨不可行，正式版应维持 v1.8 双轨设计。反馈时请附上通知栏截图与触发时间。
